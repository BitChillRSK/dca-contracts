## Security Strengths

- **Access control model**: all nine ownable contracts use `BitChillOwnable` (`Ownable2Step`, renounce
  reverts). Every handler entry point that moves value is `onlyDcaManager`, and `DcaManager` passes
  `msg.sender` as the account on every such call. Schedule ownership is checked in one place,
  `_callersSchedule` (`DcaManager.sol:594-599`); `s_dcaSchedules` is `private`, and no mutator reads it
  directly.
- **Reentrancy protection**: all 12 user-callable mutators on `DcaManager` carry OpenZeppelin's
  `ReentrancyGuardTransient`. The two swapper-only purchase entries write schedule effects before the
  handler call. `PurchaseRbtc` sets the account's rBTC slot to its sentinel before the native transfer.
- **Integration accounting**: no integrator return value is treated as cash. Deposits must change the
  handler balance by exactly the request (`TokenHandler.sol:70-75`), lending redeems must burn exactly
  the shares debited (`LendingHandler.sol:325-334`), and a purchase must consume exactly the retrieved
  stablecoin (`PurchaseRbtc.sol:66-76`). A partial MoC fill, a partial share burn, or an intermediate
  token left in the router reverts the whole batch.
- **Arithmetic safety**: Solidity 0.8.36 checked math, `SafeCast` on every narrowing storage write, and
  22 `unchecked` blocks each with a stated bound. Sampling confirmed the bounds that matter: the fee never
  exceeds the 5% cap and never decreases with amount (200,000 samples), the rBTC split never over-credits
  (50,000 batches), and LayerBank redeem sizing burns exactly the debited shares under the Pool's current
  rounding (300,000 samples).
- **Cross-user isolation**: on lending routes every outflow is bounded by the caller's own `s_shares`
  (`private`), one handler address can back only one token-route pair (`OperationsAdmin.sol:89`), and the
  handler's stablecoin must equal the pair's token. On idle routes, cash can leave only against a
  schedule balance that `DcaManager` debits first.

## Architecture Observations

- **Swapper key exposure (documented, worth one more decision before deploy)**: a window can be re-opened
  in the block the previous one ends (`DcaManager.sol:347-358`), Dex batches fall back to the 97% oracle
  floor when the caller minimum is zero, and any swapper can activate any allowlisted path. With a leaked
  swapper key these combine: users on Dex routes cannot pause or exit while windows are chained, and each
  due purchase can be filled up to 3% below oracle until the owner revokes the swapper. Each part is
  recorded as accepted; the internal review left "a mandatory gap between windows" as an open product
  decision. Contracts are immutable, so this is the last cheap moment to close it.
- **The Dex floor's "one-transaction wall" does not cover `setMocOracle`** (`PurchaseUniswap.sol:179-185`
  vs the NatSpec at `:353-358` and `IPurchaseUniswap.sol:122-128`). Replacing the oracle moves the
  effective floor in one owner call. Informational under the owner trust model; either qualify the
  comments or bound the new oracle's price against the current one.
- **Runbook note: fee collector rotation** (`PurchaseFees.sol:78-82`). `setFeeCollector` redirects future
  fees only; rBTC already credited stays with the previous address, which can still withdraw it through
  `DcaManager` at any time. Nothing is lost in an ordinary rotation. It matters only when the rotation is
  a response to a lost or compromised collector key, because the booked balance cannot be redirected.
- **Low: owner-side Dex parameters are single-step** (oracle, floor, path allowlist, swapper allowlist).
  This matches the documented governance trust; it matters most between deployment and the Safe's
  `acceptOwnership` on each contract.
- **Complexity hotspots**: `LendingHandler` rounding (ceil debit, floor value, exact burn) against
  `DcaManager`'s locked principal; `LayerBankHandler._underlyingForExactScaledBurn`, which is correct only
  for the Pool's current half-up burn (already documented with a live probe); the purchase path, which is
  deliberately outside the reentrancy guard and relies on handlers being first-party.
- **Idle routes have no handler-side per-user book.** Solvency of pooled cash rests on `DcaManager`'s
  ledger plus the two exact-delta checks. No divergence path was found.
- **Reviewer documents out of step with the code (outside `src/`)**: `AUDIT_GUIDE.md:79` says idle handlers
  keep per-user balances; `DEPENDENCY_MODIFICATIONS.md:12` says there is no `[profile.deploy]`.
